# mqttka 测试指南（WiFi 保活休眠 + MQTT 长连接）

配套固件：`bin/mqttka_keepalive_test_20261016.bin`（APP.bin 整镜像，含 Core/参数/PSRAM，1,329,680 字节，MD5 `e51c9f9936d0ec0aebd014dcf014ff94`，2026-10-16 构建；含远程抓拍、单客户端 96KB PSRAM 缓冲、事件驱动 settle；已上板验证 E2E 收图）。
测试目的：验证 TXW82x 模式 1（`SRAM_WIFI` 保活休眠）下 MQTT 长连接跨休眠存活、断点恢复唤醒（非复位）、定时心跳与远程命令闭环。

## 1. 硬件与接线

- 串口：调试烧录/串口测试点 ↔ USB 转串口，**921600-8-N-1**。
- 功耗测试（可选）：电流表/功耗分析仪串入电池供电回路，4.2V 供电。
- 相机与 TF 卡本固件全程断电，无需安装。

## 2. 烧录

**方法一（推荐，CKLink）**：板上电、无 GUI 烧录器占用 CKLink，执行：

```bat
custom\tools\burn.bat
```

烧完自动复位运行（含全量校验）。

**方法二（串口 XMODEM，CKLink 失联时的恢复路径）**：设备运行任意本系列固件时：

```bash
python custom/tools/fwupg_serial.py   # 走 AT+FWUPG，按脚本提示选 bin
```

> 注意：设备经历 dsleep 休眠循环后 CKLink 调试域会失联（串口正常），**先通过 MQTT 发 `wake` 把设备唤醒到空闲态再烧**即可恢复连接（2026-10-14 验证）；仍不行再断电重插 CKLink 或走方法二。

## 3. 上电预期

上电约 3-5 秒后串口出现横幅（UART 丢打印偶发，横幅没看到不影响功能）：

```
MQTTKA: idle. mac-derived id=ne102_xxxxxx sub=ne102/xxxxxx/cmd pub=ne102/xxxxxx/evt
  AT+KASSID=<ssid>[,<key>]    router credentials
  ...
```

LED **1Hz 慢闪**=清醒待机；4Hz 快闪=唤醒工作窗口；**全灭**=保活休眠中；2s 亮/1s 灭=故障。
默认参数：broker `broker.emqx.io:1883`，keepalive 120s，睡眠分段 90s（=keepalive×¾），主题按 MAC 生成。

## 4. 串口 AT 指令（清醒窗口有效）

| 指令 | 作用 |
|---|---|
| `AT+KASSID=<ssid>[,<key>]` | 配路由（持久化，立即重连） |
| `AT+KAMQ=<host>[,<port>[,<id>[,<sub>[,<pub>[,<ka_s>]]]]]` | MQTT 参数，缺省用默认（持久化） |
| `AT+KAGO` | 等 IP → 连 MQTT → 订阅 → 发 online |
| `AT+KASLP=<sleep_s>[,<cycles>]` | 进保活休眠循环（0=自动分段；cycles 0=不限）；需 MQTT 已连 |
| `AT+KASTOP` | 请求退出循环（下个清醒窗口生效） |
| `AT+KAPUB=<text>` | 向发布主题发任意文本 |
| `AT+KAPK=<ip>[,<port>[,<budget>]]` | 方案三 park 内心跳目标（ip=0 关闭；port 默认 9999，budget 默认 20=看门狗心跳数） |
| `AT+KAPKT` | 应用态发一条 UDP 探针到 KAPK 目标（验证网络路径，配 `park_hb_listener.py`） |
| `AT+KASHOT` | 立即抓拍一张并以 NE301 格式发到 `ne102/<mac6>/photo`（需 MQTT 在线） |
| `AT+KACAP=<0..10>` | 抓拍跳帧数（默认 3；分辨率/质量固定 1080p 管线默认） |
| `AT+KAQ` | 状态总账（两行：计数器 / 唤醒原因+轨迹+照片计数） |

休眠循环期间串口基本无响应（每周期清醒窗口只有 ~2s），控制设备优先走 MQTT。

## 5. PC 侧 MQTTX 配置

连接：Host `mqtt://broker.emqx.io`，Port `1883`，匿名，Client ID 随意（勿用 `ne102_<mac6>` 避免互踢）。

| 主题 | 方向 | 说明 |
|---|---|---|
| `ne102/<mac6>/evt` | **订阅** | 设备事件流：online / sleep / hb（含 wk 唤醒原因）/ wake / awake |
| `ne102/<mac6>/cmd` | **发布** | payload：`wake`=退出循环（休眠中可发，触发包唤醒）；`sleep`=进入循环；其它文本仅设备打印 |

mac6 从上电横幅读（本测试板 = `2313a8`，主题即 `ne102/2313a8/evt` 与 `ne102/2313a8/cmd`）。也可用命令行工具 `custom/tools/mqttka_console.py <mac6>`（订阅+交互下发一体）。

## 6. 测试流程

### 6.1 功能冒烟（~3 分钟）

1. 串口 `AT+KAGO` → evt 收到 `{"event":"online",...}`，LED 1Hz。
2. MQTTX 向 cmd 发 `hello` → 串口 `AT+KAQ` 的 `msgs` 加 1（设备只打印不回包，属预期）。
3. `AT+KAPUB=hello-from-ne102` → MQTTX evt 收到该文本。
4. `AT+KASLP=0` → evt 收到 `sleep`，LED 灭。
5. 等待观察 2-3 个心跳：每 ~90s 一条 `{"event":"hb",...,"wk":"timer"}`，墙钟间隔 91-93s。
6. MQTTX 发 `wake` → 几秒内 evt 收到 `wake`(by remote) + `awake`，设备回待机。
7. `AT+KAQ` 总账：`hb_ok` ≈ 心跳次数、`hb_fail=0`、`reconn=0`、`btrc=0`（无复位）。

### 6.2 功耗测试

1. 电流表串入后上电，完成 6.1 步骤 1（连上 MQTT）。
2. `AT+KASLP=0`，抓 ≥3 个周期（~5 分钟）：休眠段电流 + 每 90s 一个 2-4s 唤醒脉冲。
3. MQTTX 发 `wake` 结束，记录数据。
4. **判读**：本板 `ulp_half_sleep` 深层省电未启用（官方 FAE 待答），停泊电流实测若为几十 mA 属已知平台问题而非固件问题，照实留档；逻辑正确性以 evt 流为准。

### 6.3 隔夜 soak（稳定性）

1. `AT+KASLP=0` 后放置（可并接电流表）。
2. 次日 MQTTX 发 `wake`，`AT+KAQ` 读总账：
   - `cycles ≈ 经过小时 × 40`，`hb_ok ≈ cycles`，`btrc=0`（整夜无复位）；
   - `btrc=1` = 夜里发生过复位，括号内 `ph/c序号/sr` 即临终周期现场（轨迹同时持久化在设备 KV `ne102_katrace`，断电不丢），记录后反馈。

## 6.4 远程抓拍（无 SD，NE301 接收器收图）

1. **接收端**（PC）：NE301 图片接收客户端连接 `broker.emqx.io:1883`，订阅 `ne102/<mac6>/photo`（本板 = `ne102/433ba8/photo`；通配 `ne102/+/photo` 亦可）。本仓库配套：`MQTT_HOST=broker.emqx.io MQTT_PORT=1883 python custom/tools/mqtt_recv_test.py 600 ne102/+/photo`，图片落 `ne102_photos/`。
2. **触发**：MQTTX 向 `ne102/<mac6>/cmd` 发 `capture`（休眠中会先唤醒→抓拍→发布→**自动回睡**；清醒时直接抓拍）；或串口 `AT+KASHOT` 本地触发。2026-10-16 修复后休眠中触发已可靠（此前循环顶 wipe 会擦掉已锁存命令）。
3. **预期**：接收端数秒内收到 ~36KB JPEG（NE301 JSON+Base64 单发），SOI/EOI 校验通过，可直接查看。`AT+KASHOT?` 读 `photos/rc/pub/len` 探针。
4. 注意：设备可不插 SD（帧走 PSRAM stash，已启动预占）；JPEG 尾部 EOI 后填充字节由固件发布前修剪。

## 7. 判定要点（2026-10-14 板测基线）

- **保活机制**：MQTT keepalive 靠"醒来发 hb"维持——休眠中 TCP/MQTT 栈冻结，PINGREQ 发不出；协议规定客户端任何包都重置 broker 计时，PUBLISH 与 PINGREQ 等价，QoS1 ACK 还多给端到端确认。hb 只出现在唤醒窗口开头；入眠前有 3s 静默等待（消费在途命令包），不应再出现"刚睡 2s 就多余唤醒发 hb"。
- **断点恢复**：连续周期 ~92s 间隔且无复位 = 从 `system_sleep()` 调用点恢复；evt 永久静默 + AT 无响应 → 疑似复位，重启后 `AT+KAQ` 第二行 `btrc=1` 给出临终状态。
- **心跳送达**：hb 为 QoS1+等 PUBACK，broker 真收到才计数；未确认自动重连重发（evt 出现 `"rc":1` 的 hb = 自愈过一次）。勿用 QoS0 判断会话存活（实测会被静默吞掉）。
- **唤醒原因标签**：`wk` 字段仅供参考——开机后第一个周期常读作 `other`（库行为），稳态期 `timer`/`remote` 偶有混标（QoS1 ACK 尾包落在停泊边界会记为数据唤醒）；**周期间隔与心跳送达才是权威判据**。
- **时间行为**：跨休眠 jiffies 冻结不补偿（`tchk≈-89970ms` 属预期），kawaii 定时器随之冻结不误发 PINGREQ；真实 92s 间隔 < 120s keepalive，会话保持。
- **首次入眠**：偶发 ~3s 即醒（`wk:"other"`），下一周期自动正常。
- **串口打印**：唤醒瞬间与复位唤醒后的 boot 打印不可靠（板上已知），一切以 evt 流 + `AT+KAQ` + KV 轨迹为准。

## 8. 故障排查

| 现象 | 首查 |
|---|---|
| `AT+KAGO` 后故障灯 | 无凭据→`AT+KASSID`；`AT+KAQ` 看 `ip=`；路由不可达 |
| MQTT 连不上 | 公网 broker 需路由出外网；或切本地 broker：`AT+KAMQ=192.168.110.11,9991` + PC 起 `run_broker.py` |
| evt 收不到 hb | MQTTX 订阅主题拼错；设备是否真在循环（`AT+KAQ` 的 `loop=`，仅清醒窗口可读，可发 `wake` 后再查） |
| 设备完全无响应（串口+evt） | 处于休眠循环属正常（发 `wake`）；真无响应→断电重启，看 `AT+KAQ` 的 `btrc` |
| 复位反复出现 | `btrc` 行记录 ph/c/sr 反馈；检查供电是否稳定（电流尖峰） |

## 9. 恢复产品固件

本固件为 bench 构建（`custom/app/ne102_config.h` 中 `NE102_MQTTKA=1`，旁路产品 AP/Web 业务）。恢复产品行为：把该宏改回 `0` 后按仓库流程重新构建烧录，或直接烧录 `archive/` 中宏切换前的产品版本 APP.bin。

## 10. 已知边界

- 本板外部 32K 晶振（Y2）与 CKLink 引脚复用，**不得启用**（烧录会坏），RTC 用内部 RC。
- 休眠循环期间 AT 只在清醒窗口响应；`AT+KASTOP` 不如 MQTT `wake` 可靠。
- 长时停泊电流读数与 `ulp_half_sleep` 状态强相关，FAE 结论出来前功耗数据仅作相对对比。
